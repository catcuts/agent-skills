## 一、背景：这套规程要解决什么

"一总控式"多线迭代协作规程（已在"对接浪达小程序"迭代实战验证）：人类=决策者/验收者，管控会话=路由/核验/记账，N 条线会话按仓库并行开发。全部状态外置于文件（留言板、管控.md、实施记录），AI 会话本身无状态、可随时死活。

痛点：**所有会话推进都靠人类往聊天窗口打字**（发初始提示词、发"继续"、临时留言），人类离线即停摆。本方案的目标是把"驱动"从人肉聊天输入改为**文件总线驱动**：人在留言板上写字条，会话自己醒来处理。

核心设计原则（全部经实战验证）：

1. **状态外置**——会话是一次性的，任何会话死了都能从文件无损复活；
2. **留言板协议是拉取式幂等的**——指令靠"读到未标记[已执行]的就执行"消费，不靠通知。守望进程只是延迟优化：消息**不会丢，只会慢**；
3. **决策永远到人**——自动化只覆盖"机械动作"（叫醒、送信），决策/复验永远留给人类。

## 二、第一版（v1）实施方案【已定稿，当前执行】

### 2.1 人工保留的部分（用户 2026-10-16 拍板）

| 动作 | 方式 |
| --- | --- |
| 各会话初始消息 | **手动**：桌面版开新会话，按"启动卡"粘贴初始提示词（启动卡=启动文档里渲染好的每线一段，含仓库路径、职责、留言板路径） |
| 守望进程不健康时的恢复 | **手动**：收到管家弹窗/看板提示后，人工打开对应会话说一句"自检"（或贴续接模板） |

### 2.2 自动运行的部分

```
每个 AI 会话开工时（初始轮）：
  读留言板恢复状态 → 后台部署自己的守望(watch_self.py，20s轮询自己留言板) → 结束本轮
空闲态：
  守望进程轮询（零推理成本）
留言板有新写入（管控下发指令 / 人类留言）：
  守望退出 → task-notification 唤醒会话
被唤醒轮（轮纪律，不可妥协）：
  读指令区 → 执行未标记[已执行]的指令（优先级高于既有计划）→ 标记[已执行]
  → 写「## 线反馈」一次且仅一次 → 删基线重启守望 → 一句话汇报 → 结束本轮
```

### 2.3 关键纪律（实战教训成文）

1. **轮末"重扫基线"是防死循环的命门**：会话最后一件事若是写板，守望又盯着自己的板，不把本轮写入纳入基线就会自唤醒无限循环。重部署守望前**必须删基线重扫**。
2. **重扫基线前先清板上待办**：否则死窗口期到达的留言会被误吞进基线（拉取式协议天然防丢，但顺序错了会变相跳过）。
3. **无界长任务禁止**：会话一旦埋头跑长任务，期间新留言只能排队。长任务拆轮，每轮以"写反馈→重部署守望→一句话"收尾。
4. **模式B（人类↔线直连聊天）保留**：细粒度 UI 打磨（CC-18 型八轮微调）走聊天远快于走板；事后管控记账。
5. **决策类永不自动化**：自动驱动的只有"指令下发类"（指令本身已走完决策/QA流程）。

### 2.4 已实证的组件（上一迭代遗产，直接复用）

| 组件 | 位置 | 设计要点 |
| --- | --- | --- |
| 留言板守望脚本 | `.sprints/对接浪达小程序_20260912_090100/tmp/watch_board.py` | 20s stat 轮询 mtime+size → 变化即打印退出（触发 task-notification 唤醒）；5min touch 心跳文件；12h 无变化"平安超时"退出防僵尸；持久化基线 json 防漏报 |

## 三、理想态（v2）全自动化方案【已验证可行，未实施】

### 3.1 分层架构

```
Tier 0  守护进程 guardian（OS 级，0 token，开机自启/任意会话初始轮幂等拉起）
        职责：轮询中央注册表 → 守望健康巡检（心跳文件mtime）→ 各线超时检查
              → 计费提醒 → 异常时：写救援flag + Windows toast 弹给人类
        注意：不自己重启守望（会产出"孤儿守望"——能检测不能通知，唤醒链只有
              会话亲儿子后台进程能续）；只探测+flag+弹窗
Tier 1  板守望（会话亲儿子后台进程，0 token）——不变
Tier 2  守卫轮（会话内预注册低频自动化，极小轮）——心跳的替代品
        提示词："读救援flag，不存在则静默结束；存在则：先清板上待办（拉取式防漏），
                再杀孤儿守望 → 重部署亲儿子守望 → 清flag"
        频率 60~120min（每轮都会重喂会话全历史，间隔是成本必需而非优化）
Tier 3  救援（人类，toast 触发）——秒级恢复路径
```

### 3.2 驱动通道（按优先级）

| 通道 | 适用 | 状态 |
| --- | --- | --- |
| **app-server 协议**（常驻进程，见 §五） | v2 主路径：开会话（指定模型）/送信/列表/权限中继，全参数化 | ✅ 端到端实测通过 |
| CLI 无头调用（`--resume <sessionId> -p "msg"`） | 简单唤醒/送信；**模型跟会话走**（resume 不改模型） | ✅ 实测通过 |
| cron/自动化（守望自驱动） | 无 CLI 环境的兜底 | ✅ 实测通过 |
| 人类 toast + 手动一句"自检" | 最终兜底 | ✅ 实证 |

### 3.3 命名规范（"心跳"一词退役到进程层）

- **守望**=盯留言板的会话子进程；**守护**=OS 级管家；**守卫轮**=低频兜底自动化；**自愈**=守卫轮做的事；**救援**=弹窗找人类。
- "心跳"只指守望 touch 的心跳**文件**（免费信号），不再指任何 AI 层周期消息。

## 五、踩坑全记录（现象 → 原因 → 解法）

1. **系统 Node 直接跑 zcode.cjs 报 "No such built-in module: node:sqlite"**
   → CLI 需要新 Node。解：`ELECTRON_RUN_AS_NODE=1 G:\software\ZCode\ZCode.exe <zcode.cjs> [args]`，用桌面版自带 Electron 运行时。正式使用建议按官方安装脚本装 `zcode` 命令。
2. **桌面版会话列表看不到 CLI 开的会话**
   → 同一个数据库（文件 ID 实测相同+跨越写入立即可见），但列表**不实时刷新**。解：重启桌面版/切换工作区后出现（待最终确认）。另查实 `C:\Users\catcuts\.zcode\cli` 本身是**指向 `H:\.zcode\cli` 的符号链接**（用户迁移数据所留），两个路径同一物理存储，混用不会两套账。
3. **无界面模式选模型不受控**
   → `defaultModelSelection`（H:\.zcode\v2\provider_config.json）被 -p 无视（改成 kimi-k2.6 做诱饵仍选 kimi-k3，实锤）；无 --model 参数；/model 斜杠不路由。规则：**-p 取 providerOrder[0] 的 modelOrder[0]**。
   → 解法：a) 路径1 用桌面开正式会话（模型人选），命令行只 resume；b) 个人配置加 bigmodel API Key 并排 providerOrder 第一；c) v2 用 app-server（create/send 均可带模型）。
4. **app-server 会话创建超时 -32022 "session/requestRuntimePreferences"**
   → 协议**双向**：服务端会向客户端反向发请求，客户端必须逐条应答。应答体：`{nativeSearchEnhancementsEnabled:false, memoryEnabled:false}`（参考 packages/desktop/scripts/mcp-apps-host-fixture/agent.ts）。
5. **回合卡死：interaction/requestOfficialMcpAuthHeaders 反复重发**
   → 此类请求**不能用 JSON-RPC error 拒绝**。正确应答：`{ok:false, reason:"official_auth_unavailable"}`（源码注释：缺省一律如此，绝不降级匿名）。
6. **权限请求**：`interaction/requestPermission` → 应答 `{decision:"allow"|"deny"}`。启动台必须按策略转发给人类（决策到人原则的协议落点）。
7. **文档骗人：`turn.completed` 事件不存在**（本版本）
   → 真实终结信号：带 `payload.response` 字段的终结事件（含 usage/tokenCount）。流式增量事件也无 type 字段，靠 payload 形状区分。**一切以抓包实测为准**。
8. **不订阅收不到事件**：session/send 成功 ≠ 有事件流，必须先 `session/subscribe`。
9. **裸 app-server 注册表没有账号型 Provider**（"Provider Registry 中不存在 Model: account:bigmodel-individual-coding-plan/GLM-5.3-Flash"）
   → 账号 Provider 是桌面版作为 host 经 `provider/updateAccountConfig` 推送的。解：照桌面复刻推送，或个人配置加 API Key 型 Provider。
10. **模型要求推理档位**：部分模型（如 kimi-k3）create 时必须带 `options:{reasoningLevel:"max"}`，否则 ModelProtocolError。
11. **CronUpdate 不能暂停自动化**（enabled 不可改）；需要"暂停"就删除重建，或用守卫式提示词（读 flag 静默退出）。
12. **heredoc / node -e 写多行替换会坏文件**（转义层数不可控）：写脚本用 Write 工具；路径一律正斜杠（Windows API 全兼容）。
13. **H:\.zcode\v2\provider_config.json 含明文 API Key**（Kimi）：该文件是个人 Provider 配置的权威源，勿外传、勿入 git。
14. **watchdog 两类死法要分清**：本机休眠杀守望（cron 兜底自愈已实证两次、零漏报）；harness 进程崩溃则守望陪葬（唯一真空洞，靠人类贴续接模板复活——已实证多次无损）。

    let m; try{m=JSON.parse(line);}catch(e){continue;}
    if(m.id!==undefined && m.method){            // 服务端反向请求：必须应答
      let result=null;
      if(m.method==='session/requestRuntimePreferences')
        result={nativeSearchEnhancementsEnabled:false,memoryEnabled:false};
      else if(m.method==='interaction/requestOfficialMcpAuthHeaders')
        result={ok:false,reason:'official_auth_unavailable'};   // 不可用 error 拒绝！
      else if(m.method==='interaction/requestPermission')
        result={decision:'deny'};               // 生产中应转发人类
      else {child.stdin.write(JSON.stringify({id:m.id,error:{code:-32601,message:'unexpected'}})+'\n');return;}
      child.stdin.write(JSON.stringify({id:m.id,result})+'\n');
    }
    else if(m.id!==undefined && pending.has(m.id)){const p=pending.get(m.id);pending.delete(m.id);p(m);}
    else if(m.method==='session/event'){events.push(m);}
  }
});
function rpc(method,params,timeoutMs=90000){return new Promise((resolve,reject)=>{
  const id=nextId++; pending.set(id,resolve);
  child.stdin.write(JSON.stringify({id,method,params})+'\n');
  setTimeout(()=>{if(pending.has(id)){pending.delete(id);reject(new Error('timeout:'+method));}},timeoutMs);});}
function waitResponse(timeoutMs=180000){return new Promise((resolve,reject)=>{
  const t0=Date.now(); const iv=setInterval(()=>{
    const hit=events.find(e=>typeof e.params?.payload?.response==='string');
    if(hit){clearInterval(iv);resolve(hit);}
    else if(Date.now()-t0>timeoutMs){clearInterval(iv);reject(new Error('response timeout'));}
  },400);});}
(async()=>{
  const created=await rpc('session/create',{
    workspace:{workspacePath:W,workspaceKey:W},
    model:{providerId:'moonshot-kimi',modelId:'kimi-k3',options:{reasoningLevel:'max'}},
    titleGenerationEnabled:false});
  const sid=created.result.session.sessionId;
  await rpc('session/subscribe',{sessionId:sid,deliveryKind:'desktop-continuous',includeSnapshot:true});
  await rpc('session/send',{sessionId:sid,inputId:'inp_1',
    content:'你的任务提示词', modelSelection:{providerId:'moonshot-kimi',modelId:'kimi-k3',options:{reasoningLevel:'max'}}});
  const done=await waitResponse();
  console.log('回复:',done.params.payload.response,'| tokens:',done.params.payload.tokenCount);
  const lst=await rpc('session/list',{});
  console.log('全会话:',lst.result?.sessions?.length);
  child.stdin.end(); setTimeout(()=>process.exit(0),800);
})().catch(e=>{console.log('FAIL:',e.message);child.kill();process.exit(1);});
