# 多会话协作规范

> 适用范围：同一迭代/批次内两个以上 AI 会话并行工作的场景。编号体系、状态块、修订留痕、验收清零以《项目协作约定》为准。

## 1. 形态铁律

- **线 = 责任域 + 文件档案**：一条线守一个（或一组强耦合）项目的开发责任；它的全部状态在线迭代目录的文件里（留言板、实施记录、环境与工具链、契约、回炉说明）。**线不等于会话。**
- **会话 = 按批分配的临时工作空间**：总控把一批任务派给一个会话（在所属仓库目录中开），会话装载线档案干活，批毕交付即终；后续问题作为新任务开新会话，即插即用。禁止"一条线一个会话走到黑"的默认心智。
- **同线多会话的关系＝并列（常态）**：新批任务开新会话，会话之间无接替关系，只共享线档案（文件）——任一会话的上下文对其他会话不存在，一切知识经线档案传递。
- **批内续接（异常兜底）**：批未完成而会话先撑不住（上下文溢出/腐烂）→ 开续接会话接完本批（读线档案＋批内状态恢复）；正常应靠批粒度划分避免。
- **一线一档**：并列与续接的会话**续写同一线进度文件**，不封存不分叉（接替/新批在时间线登记）；仅当线拆分或退役时封存旧档、拆出的线各立新档。
- **不得用会话内子智能体 / workflow 编排替代多线形态**，除非用户明示要求。
- 为什么：文件是唯一事实源，会话可死可换；短命会话每批只装载所需上下文（长寿会话每次唤醒重喂全部历史，越活越贵）；批批新鲜上下文，避免隐性误解累积。
- 会话内子代理仅限一次性辅助任务（环境部署、批量构建等），不可向人类提问，失败即返回问题报告（已执行步骤/失败点/原因/建议）。

## 2. 会话角色

- 人类：决策者与验收者。批复决策、复验证据、外部协调、按总控的时机表开批/发指令。
- 管控会话：任务编排、批分配、回执独立核验、跨线分流、状态外置记账；**守望与兜底的唯一部署方**；不参与业务开发。
- 批工作会话：承接某线的一批任务，在所属仓库目录工作——读线档案 → 执行 → 按交付清单收口（§15）→ 批毕即终。细粒度打磨可由人类直连该会话（直连模式，§14）。
- 一次性子代理：环境部署等独立任务，跑完即弃。

## 3. 留言板（跨会话通信唯一通道）

- 每线一块，三区：
  - `## 管控指令`：管控会话写，带序号+时间戳；批工作会话执行完毕后原地标记[已执行]。
  - `## 线反馈`：批工作会话一条消息结束时写一次且仅一次，过程中不写。
  - `## 待确认`：批工作会话写，编号+背景+可选项，由管控会话分流（QA 自答留痕 / QB 升级人类）。
- **指令状态粒度**：批会话接受指令后，先在「线反馈」区登记一行（`开始 #N，{{时间}}`）再动手——执行中状态必须在板上可见；执行完毕才在指令区标记[已执行]。
- 跨会话不直接修改对方产物；一切经留言板或人类转交。

## 4. 轮纪律

- 轮开始：读本线留言板「## 管控指令」，执行未标记[已执行]的新指令（优先级高于本批既有任务）。
- 轮结束：写「## 线反馈」→ 清板上待办 → 一句话汇报。**守望由总控常驻部署，批会话不部署、不重启守望。**
- 禁止无界长任务，长任务拆轮；**超出本批范围的工作不扩批**——登记为新任务交总控派新会话。

## 5. 守望与兜底（总控部署）

- 守望与定时兜底全部由总控部署（盯全部留言板）；批工作会话不管守望。
- **场景A｜写板方轮末重部署**（总控自己刚写完板）：清板上待办 → **删基线** → 重部署。目的：把本轮自身写入烘进基线，防自唤醒死循环。
- **场景B｜兜底重启**（守望死亡/疑似漏报）：**不删基线**直接重启。守望启动自检会与基线比对，死亡窗口期漏掉的变化立即报告并退出、唤醒总控；删基线反而把漏报烘进新基线。
- **兜底心跳流水**：定时兜底每次巡检追加一行至迭代目录根的 `总控-心跳日志.md`（总控专属文档·兜底独写·追加式；时间＋事件：兜底重启守望/久无反馈提醒/状态通报），供总控与人类回溯巡检史，管控台账 §6 仍由总控独写、兜底不写入；判活用的心跳文件（watch_heartbeat.txt）属临时状态文件（§13）。
- 兜底提示词模板见 assets/兜底心跳提示词模板.md。

## 6. 执行纪律（长命令）

- 构建/编译/打包/安装/部署等长命令一律后台执行，**禁止固定时长等待**（如 sleep 10 分钟后去看输出）。
- 先识别该命令的**结束标志**（命令输出、过程日志内容、接口响应中的完成/失败特征），以纯脚本轮询循环（10~30 秒一次）等待标志；命中即继续；仅最大超时（如 10 分钟）后才返回 AI 处理。
- 通用等待脚本：assets/wait_for.py（支持命令输出文件、日志文件、HTTP 响应三种标志源）。

## 7. 写入时序

- 写板前重读锚点，写后复读标记归属。
- 共享文档修订前先读其状态块；新版本行按版本号倒序插入。
- 多会话禁止同时编辑同一文件：读到某线正在修订的登记即串行等待。
- 台账类 CSV 单写者（见《信息记录规范》写入纪律）。

## 8. 总控输出契约（管控会话每次回复生效）

- 每次回复**末尾**固定带「各线指令」区：无指令也要明写"无"，不得省略该区。
- 每条线的指令各自放一个**独立代码块**，便于直接复制；多条线不得挤在同一块。
- 指令**自包含**：写完整内容，禁止"沿用上一条""在上一条上追加"等需要人类回翻或自行拼接的写法。
- 同附「依赖/时机一览表」：**按发送顺序**排列，每条注明"现在发 / 等 X 后发 / 暂不发（原因）"，包括"是否现在开批"。
- 指令 = 需要会话**执行动作**的消息；纯告知/背景更新不进指令区（并入进展说明），除非某线正等该信息解锁。
- 结构化信息（状态、依赖、清单）优先用表格呈现。
- 本节只约定回复**结构**；回复**语言**（可懂性：编号转译、摘要开头、叙事过渡）按《沟通规范》执行。
- **指令发出即登记《指令台账》**：一行一条（#N | 日期 | 目标线 | 来源＝总控/用户直连 | 摘要 | 状态），总控重续、批会话重开、交付对账均以此为准，不依赖聊天记录（格式与分级见 §16）。

## 9. 契约先行

- 拆线方案批准后、各线开工前，总控牵头产出**跨线契约文档**（assets/契约文档模板）：**协议**（跨交互点的通信与流程约定：认证、时序、主题/指令命名规范、码表）＋ **接口**（可独立描述的交互点，带交互形态字段：HTTP / 消息主题 / 长连接指令 / 回调 / …），经人类批准后冻结为基线版。
- 契约完备性判据 = **可 mock 三条件**：①能造出合法样例；②能校验对方发来的内容；③能处理异常。逐接口对照模板最小要素表检查，缺任一即契约未完成（消息型接口的码表就是它的"错误码+出入参"，缺了就是没契约）。
- 各批会话**基于契约隔离开发、基于契约 mock 自测**（各端分离/隔离开发模式）；契约自测通过是联调开启条件之一（§10）。
- 契约变更必须走管控登记（编号 + 通知受影响线重评），禁止两线各自漂移。

## 10. 联调线与冻结窗口

- 拆线典型线型：开发线×N ＋ **联调线**（集成验证）＋（可选）设施/环境线；集成验证统一由联调线执行，禁止"各线各联调各的"。
- 联调批开启条件：各开发线已备齐联调条件——**基于契约的开发与 mock 自测完毕**、部署包/安装包/部署与安装脚本等就绪；缺什么回流对应线补齐，联调批只关注联调本身。
- **冻结窗口**：联调期间其它线冻结代码变更（联调批独占环境与代码读态，避免写读脏读与互相踩踏）；联调发现的缺陷回流对应线，修复并确认后再继续联调。

## 11. 初始化即任务（两级 T0）

- **总控 T0（脚手架）**：冷启动的脚手架工作（迭代目录/留言板/管控台账/任务卡产出/守望与兜底部署）是实施计划的**首个任务包 T0**，由总控执行、纳入实施记录——不得作为"计划外前置动作"游离于计划之外。
- **线级 T0（环境就绪批）**：每线实施的**第一个批**，完成前不启动功能开发。内容：①工具链就位（语言运行时/包管理器/构建工具）；②项目能运行——构建通过/服务能起/冒烟命令跑通，完成标准必须**可验证**；③产出《环境与工具链.md》（assets/环境与工具链记录模板：安装步骤、运行命令、版本要求、踩坑记录）。该文件即本线的**项目记忆**——环境知识不依赖会话记忆，每批新会话直接读它；有跨迭代复用价值的环境流程，沉淀进 flows.csv。批量档同理。

## 12. 回执与核验纪律

- 回执勿美化：描述与实测证据一致；界面类"通过"只认可见内容。
- 核验提示词中性：不得含预期值。
- 拿不准是否属重构级 → 按重构级中止，输出回炉说明。

## 13. 临时文件纪律

- **迭代目录布局**（总控 T0 建立）：① 迭代目录根＝**全局文档区**：实施计划/实施记录/项目协作约定/指令台账/契约文档/总控-心跳日志.md/验收报告/复盘报告——人类可读、按版本留档；② `lines/`＝**线归属的流水档案**：线进度文件（`线X-<标识>.md`，线独写）、`初始提示词-线X.md`（总控 T0 产出、线装载）、`交接-线Xto线Y.md`（线独写、全线共享）——追加式续写，命名「归属-名称」；**非线归属的流水不入 `lines/`**（总控的巡检流水在根的 `总控-心跳日志.md`）；③ `tmp/`＝临时状态区（见下）。
- **目录规划**：迭代级临时物 → 迭代目录 `tmp\{用途}\`；**守望状态文件（基线/判活心跳/命令日志）放总控专属 tmp**；严禁多守望共用同一 watch_baseline.json / 心跳文件（互踩漏报）。
- **禁地**：严禁在项目/仓库根目录散落任何临时物。
- **命名**：`用途_日期`（如 `构建等待_1116.log`），禁无意义名（1.txt、test.log）。
- **生命周期**：轮末顺手清本轮 scratch；批交付清单含 tmp 本批残留清理（§15）；收尾序列做 tmp 总清点；复盘时 tmp 只允许存在可解释残留。
- 通用工具（watch_board.py / wait_for.py）从技能 assets 复制到 tmp 使用，不各处重造。

## 14. 直连模式（人类直连会话沟通的三层保险）

- 人类可直接与任一批工作会话对话（细粒度打磨、追问、临时调整）；总控默认不在场，靠三层保险保账：
- **第一层｜临终交付清单（结构性收口）**：批会话结束前的交付清单（§15）必含"**本会话期间与人类的直连沟通摘要**"，写入留言板「线反馈」——不写则随会话消失；总控批核验发现缺失即打回。
- **第二层｜人类一句双保险**：直连中形成决策级结论时，人对会话说一句"**记到板上**"。
- **第三层｜总控对账兜底**：批交付核验（§15）时对照提交/文件变化与板上已知任务，发现**未登记的变更**即询问归属。
- 分级：**信息级**直连（微调、追问、闲聊）登记摘要即可；**决策级**直连（改范围/改契约/改优先级）必须落板走 DC 编号，否则视为未发生。
- **入账分级与流向**：任务级/决策级直连 → 批会话登记（进度文件+留言板，标注"来源＝用户直连"）→ 总控对账后入《指令台账》（§16）；信息级不单独入账，批临终清单摘要带过。

## 15. 批与交付核验

- **批粒度**：一个批 = 一个连贯工作单元（如 T0 环境批、某功能批、缺陷修复批、联调批）；大到人类不必频繁开窗口，小到批内不需要中途更换上下文。
- **批生命期 = 会话生命期**：会话随批开始而开、随批交付而终；批内确需多轮交互（如联调批）同一会话贯穿即可。
- **交付清单**（批会话临终前逐项完成）：①代码/文档提交；②留言板回执（含直连沟通摘要）；③实施记录更新（任务终态+偏差登记）；④有沉淀价值的进 flows.csv/环境记录；⑤tmp 本批残留清理。
- **交付核验关卡**（总控执行）：提交、板、实施记录**三对齐**——有提交无回执、有回执无记录、有变更无登记（含直连遗漏）均打回补齐；通过后台账销批，必要时开新批。

## 16. 指令台账（两类来源的统一留痕）

- **目的**：让"总控安排的指令"与"用户直连下达的任务/决策"都留下文件痕迹——总控重续、批会话重开、交付对账均以此为准，不依赖聊天记录。
- **位置**：迭代目录 `指令台账.md`（追加式；总控发出即登记；用户直连条目由批会话登记、总控对账后入账）。
- **一行一条**：`#N | 日期 | 目标线 | 来源（总控/用户直连） | 内容摘要 | 状态（已下发/开始/完成/取消）`。
- **序号空间**：每线一个统一序号（不分来源混排）——批会话在留言板/进度文件登记的"开始 #N"引用同一序号。
- **分级**：任务级/决策级必须入账；信息级（追问/闲聊/措辞微调）不入账，批临终清单摘要带过。
- **判据**：看消息性质不看出处——让某条线执行动作的都算指令，无论由总控起草还是用户直发。
