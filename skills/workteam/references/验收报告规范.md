# 验收报告规范

> 适用范围：本项目各迭代的验收报告（含内部代行验收与需求方正式验收）。
> 目标：验收报告只回答三类问题——**验了什么、怎么验的、结果如何**；让首次接触本项目的读者不借助任何内部文档即可读懂。

## 1. 定位与读者

- 验收报告是对"交付物在验收时点是否满足验收标准"的正式记录。
- 默认读者：验收相关方（需求方、管理层、后续维护者），**默认其首次接触本项目**，不了解开发过程与内部协作方式。
- 报告必须自包含：环境、术语、数据、入口均在报告内交代清楚，不要求读者翻阅实施记录或技术方案。

## 2. 内容边界

**只写：**

- 验收范围与方法（验什么、怎么验、判定标准）
- 验收环境（构成、入口、账号与角色、测试数据）
- 验收过程与结果（按业务域或业务流程组织）
- 问题清单（现象、影响、定性、验收时点状态、归属——见 §6）
- 遗留事项与条件项
- 验收结论
- 附录（证据清单、术语表）

**不写（这些属于实施记录/过程文档）：**

- 内部协作过程：任务或指令编号、会话与工作线代号、回执、轮次
- 缺陷修复过程：谁修复的、修复提交、修复与复验的轮次
- 报告自身的修订过程：更正声明、"按 XX 复核后修订"等版本过程词
- 过程性词汇：补验、重走、复验、初版、终版、二次修订等
- 验收时点之前已不存在的中间环境与中间状态（环境描述以验收当时为准）

## 3. 结构骨架

| 章节 | 内容 | 要点 |
| --- | --- | --- |
| 头部 | 产品/迭代名称、验收范围、报告日期、验收方、编写方 | 一眼可归档 |
| 1. 验收概述 | 产品形态与应用场景定位、验收目的、**结论摘要** | 开篇即建立图景与结论 |
| 2. 验收范围与方法 | 范围清单（含明确不在范围者）、方法、判定标准 | 范围与标准先于过程 |
| 3. 验收环境 | 环境构成（表/图+说明）、访问入口、账号与角色、测试数据说明 | 前提完整、可复现 |
| 4. 验收过程与结果 | 按业务域分节；每项=过程描述+结果判定+证据引用 | 事实先行、判定随后 |
| 5. 问题清单 | 见 §6 | 只记现象与时点状态 |
| 6. 遗留事项与建议 | 未验项、外部依赖、处理建议；每项注明责任方与触发条件 | |
| 7. 验收结论 | 结论分级+依据，可追溯到正文 | 见 §7 |
| 附录 A 证据清单 | 证据文件与内容的对应索引 | |
| 附录 B 术语表 | 术语与缩写定义（正文首现处解释，或统一前置于此） | |

## 4. 措辞规范

1. **称呼与实物当前形态一致**——标题与通篇定位反映交付物当下的形态与规模，不沿用早期阶段或旧用途的叫法。
2. **不使用环境专属称呼与内部代号**——只在特定部署、特定协作语境里才有意义的称呼（工作线代号、任务编号、内部缺陷编号、里程碑代号等）不得出现；一律转译为角色名、功能名或业务语言。环境标识（IP、租户 ID 等）仅在环境章节与证据中出现；正文如需指称具体测试对象，首次绑定后通篇使用角色化称呼（如"测试租户 A（tenantId=11）"）。
3. **术语首现必须先解释**——缩写、代号、专有名词在第一次出现处就地定义，或以术语表前置。
4. **操作描述补全执行者与作用对象**——凡"做某事"的表述写明谁来做、对哪个对象做（如"以管理员账号登录管理端，创建代理型客户"）。
5. **前提条件完整**——环境与数据章节覆盖全部需事先就位的角色、账号与材料，每项注明归属与要求，不默认读者已知。
6. **状态口径统一**——一切状态以验收完成时点为准；不出现"修复前/修复后""复核前/复核后"的过程对比叙事（问题现象以问题清单方式记录，见 §6）。
7. **事实与判定分离**——先描述观察到的现象，再给判定；判定不得超出证据支撑范围，正文未支撑的内容不得进入结论。
8. **图表必须配解释**——每张截图/图表的引用处用一句话说明该证据展示了什么、证明了什么，不允许裸放。
9. **同一信息只在一处展开**——重复出现的内容合并为一处，其余位置以引用代替。
10. **章节之间要有过渡**——章与章之间有承接性表述（逻辑关系、递进关系显性化）；任何章节要么融入主线，要么以附录式定位收尾，不允许悬空的信息块。
11. **语气客观平实**——不美化、不辩解、不内部叙事；用主动语态与具体数字，避免"基本正常""大致可用"类模糊表述。
12. **文风按读者动作分级**——判定性内容（结论、结论摘要）与登记性内容（范围/环境/清单/附录）用规范简洁体；解释性行动指引（遗留详细说明、问题影响说明）用"现状—不处理的后果—需要谁做什么"的叙事体，平实口语化到未亲历者可独立理解并据此行动。判据：这段话的读者是否要据此行动或决策——要则叙事，不要则规范。
13. **多系统共存时归属/责任方用完整系统名**——报告涉及两个以上系统（如 Voerka多租户云平台与 Voerka平台租户实例）时，问题清单归属、遗留责任方等行动指派字段必须使用完整系统名（可带侧别括注，如"Voerka多租户云平台（管理端后端）"），不得使用裸"平台/平台端/平台侧"指称；两系统的产品界面复合词（平台管理端/平台门户等）不受限，但须在术语表中定义归属。

## 5. 证据规范

- 证据存放于报告同目录的 `证据/` 子目录；文件名语义化（`系统-页面/场景-要点`），不含内部编号与过程词。
- 每份证据必须被正文引用并配有结果判定；未被引用的证据不放入证据目录。报告发布与每次修订后，应核对引用与文件双向一致（无失效引用、无孤儿文件）。
- 截图应完整可辨，保留必要上下文（页面标题、地址栏、关键区域）；敏感信息（密码、密钥）打码。
- 页面/屏幕类证据须随附可复现的访问地址（完整 URL，含前端路由）：表格呈现时单列访问地址，行文呈现时写明于证据引用处；地址须实测核验，不得臆写。
- 同一章节内并列的多个证据表应使用一致的表头结构，不因来源或采集批次不同而异构。
- 证据表内逐行写实，不用"同上/同首行"等省略式引用——每行独立给出完整证据（图/文件引用或明确的文字说明），读者无须回翻对照；无对应证据的行如实写明（如"真机期补拍"），不用省略符号代替。
- 界面类证据的说明须点明**图中可见内容与场景输入/接口出数的对应关系**（如"图中实时值 75 即注入的心率 75、对应 API-26 的 xl=75"），使读者能据此核对截图与判定是否相符；图中**没有**体现的 claimed 内容（如取证时未注入该类数据）须如实注明，不得让图"默认代表"场景。表格中证据引用与说明文字**分列**呈现（如"界面显示"列只放图/文件引用，"说明"列承载对应关系文字），说明文字不用括号包裹。
- 证据缺口说明须写明**缺口的真实性质**，不得含糊：属"可模拟但未覆盖取证"的写"补拍中/未覆盖"；属"产品无对应界面/功能面"的写明"无对应页面并说明原因"；属"依赖真实环境"的写"待真机期"。三者不得混用"待复核"等模糊表述，避免读者误读为技术限制。
- 表格内的长文本（接口出数、说明等列）**分点列写**（用①②编号并以换行分隔；多图逐图以"图一/图二"指代，各自成点），不整段复写。
- 验收正文（矩阵/结论/问题清单/遗留）与证据文件名**不得出现过程词**（修复、复拍、补拍、重拍、纠偏等）——过程信息只写入成果记录或实施记录；正文与文件名只呈现结果状态（如证据文件以"系统-页面-要点"命名，不加"修复后"后缀）。
- 文本类证据（接口响应、命令输出）注明采集时间与所属环境；文本内容同样不得含内部编号与过程词。
- 证据注明所属构建/版本；报告版本更替时，受影响证据重新采集或在说明中标注构建身份，不得沿用无法确证时点状态的旧证据。

## 6. 问题清单与遗留事项规范

- 问题清单只收录**验收时点仍未解决**的问题（登记遗留、待外部条件，或已规避但仍有持续影响者）。
- 开发内部验收中，验收期间发现且已在验收时点前解决的缺陷属开发过程产物，记入实施记录，**不进入问题清单，报告内亦不为其留统计或摘要句**；其问题现象证据随之移入 `存档/被替代证据/`。
- 每条问题包含：现象（含证据引用）、影响、定性（原因归类）、状态、归属建议；**影响列用平实语言写明落到用户/界面的具体现象与后果**（如"小程序健康弹窗会把字面量 null 当文本显示出来"），不写抽象概括。
- 遗留事项表设"详细说明"列：事项列只放短名，详细说明按**"现状—不处理的后果—需要谁做什么"**的叙事写法用平实语言成段（如 L5 体例：先说现状已对齐的部分，再说未确认的风险及其落到用户的现象，最后点明所需确认动作），使未亲历验证过程的读者可独立理解并可据此行动；说明不得依赖内部代号或会话上下文。
- 状态枚举：登记遗留 / 待外部条件 / 已规避（有持续影响）。
- 报告内使用自有编号（如 P1、P2），不沿用内部缺陷编号；内部编号的映射由实施记录承担。
- 需求方正式验收如契约上要求全量缺陷台账（含已修复项），以正式验收文档的约定为准，不适用本节。

## 7. 结论规范

- 结论分级：通过 / 有条件通过（列明条件项）/ 不通过（列明阻断项）。
- 结论的每一条依据都能在正文找到对应的过程与证据。
- 条件项与遗留项写明责任方与解除条件。

## 8. 版本与修订

- 报告版本以时间戳标识，版本目录与报告文件同名（`验收报告_YYYY-MM-DD_HH-MM-SS/验收报告_YYYY-MM-DD_HH-MM-SS.md`）。
- 修订过程（谁改了什么、为什么）记入实施记录，不写入报告正文；报告内不出现修订声明。
- 验收通过后报告冻结；后续变更以新版本目录发布，旧版本目录整体移入 `存档/旧版报告/`——任一历史版本保持独立可复验。
- **版本目录（报告自包含）**：每份报告始终位于与其同名的版本目录中，目录内含报告文件与其引用的 `证据/`。证据目录只属于该份报告（物理归属，而非共享素材池）；报告内证据引用一律用相对路径，版本目录整体移动不影响链接。
- **修订期证据替换**：替换证据时，旧件先移入 `存档/被替代证据/`、再写入新件——**禁止同名原地覆盖**（旧内容将无副本丢失、无法追溯）。被替代证据是某版报告修订过程的中间产物，不构成独立报告版本，单桶存放即可。
- 存档附 README 说明其性质与收录范围；被替代证据可能与在用报告的证据**同名不同内容**——存档 README 须声明"同名文件一切以在用报告版本目录内 `证据/` 为准"，防止查阅时混看。
- 头部报告日期随版本目录更替同步更新，纳入呈送前一致性核对。
